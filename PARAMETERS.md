# Open parameters (Master Spec Part O)

The spec lists eight decisions (Part O) that must be made before Phase 1
and that materially change the build; #9 below was added during the
build itself once it became a real, concrete choice rather than an
abstract one. To keep moving, each has been given a **default** below so
the code has concrete numbers to work with. Most of these live in
`backend/app/config.py` as named settings, so changing one is a config
edit, not a refactor — #9 in particular is an architectural choice, not a
config value. **Treat every value here as provisional until you confirm it.**

| # | Question | Default chosen | Rationale / what changes if you pick differently |
|---|---|---|---|
| 1 | Capital base | **LKR 25,000,000** | Mid-point of the capacity curve the spec describes (LKR 5m–200m). Sets `MAX_POSITION_PCT_OF_ADV`, liquidity gate thresholds, and position caps in §11.1/§27.1. If your real capital is under ~10m, the liquidity gate (median daily turnover ≥ LKR 2.0m) should probably tighten; if it's over ~100m, it should loosen and the concentration caps matter much more. |
| 2 | Historical data depth | **2015-01-01** as the earliest point-in-time backfill target | Matches the spec's own estimate ("2015-onward may be clean, earlier patchy," Part O #2). Backtests before this date are not attempted. Note 17 Aug: financial-statement history is now genuinely reachable back to 2012 via `/api/financials` (`financial_reports_archive_loader.py`), but **only files from ~2019 onward actually download** — everything 2018 and earlier 403s from CSE's own CDN despite being catalogued. So the practical financial-statement floor is closer to 2019 than 2015, regardless of this target. |
| 3 | Broker execution | **Manual** (system computes the entry ladder and displays it; no order is ever placed programmatically) | Consistent with Design Law 6 (§4) — no BUY button, no write access to order flow, ever. This is not really an open question given the design laws; it's fixed regardless of broker API availability. |
| 4 | Tax treatment | **Not modelled yet** — `net_return` in the decision/outcome record is post-fee, pre-tax | Sri Lankan capital-gains treatment depends on your residency and holding structure. Flagged as a TODO on the `outcomes` table rather than guessed. |
| 5 | Second data source | **Partially resolved 17 Aug: a genuine external second source exists for TODAY'S close, not for historical depth.** `app/jobs/second_source_reconciliation.py` cross-checks each day's captured close against TradingView's live quote for the same CSE line (`CSELK:<ticker>`, via TradingView's `/global/scan` — the one path its own robots.txt allows) and raises the same `DataAlert`/quarantine Part II §5.2 asks for on a >0.5% mismatch. This is a real institution with no relationship to cse.lk, so it satisfies §5.2's "nightly cross-check against a second source" literally. What it does NOT give: TradingView carries a live quote only — its own chart renders no historical candles for CSE symbols at any timeframe — so there is still no independent way to verify or backfill anything before today, and the internal-only note below still applies to history. Do not confuse either of these with the 17 Aug per-company price-history backfill (`companyChartDataByStock`) — that solved *depth* (1 day → ~241 sessions) but is still cse.lk, the same single institution; it is TradingView, not that backfill, which is the actual second source. `app/jobs/reconciliation.py` remains the *internal* check only (adjusted-vs-raw from our own confirmed corporate actions) — corrected 16 Aug: an earlier version of this row claimed a pluggable `SecondarySource` interface existed; it doesn't. | This is a real operational risk per §5 ("the single biggest operational fragility") and Part II §5.2 ("nightly cross-check against a second source... discrepancy >0.5% quarantines the ticker"). Live capture risk is now materially reduced; historical backtest risk is not. Cheapest remaining route to closing the historical gap: a broker EOD file. |
| 6 | Dividend policy | **Total return** (dividends reinvested in the adjustment-factor series; DDM/FCFE anchors weighted per archetype table in §24, not overridden toward income) | If you're optimising for income rather than total return, the triangulation weights in §24 would need a distinct "income" profile. Not built. |
| 7 | Concentration appetite | **8–15 positions**, tier caps 10% / 6% / 3% (Tier 1/2/3) | Taken directly from §27.1 and §39.1 defaults. |
| 8 | Sector exclusions | **None encoded** | No sectors/structures are hard-excluded beyond the integrity and structural gates (§11.1). Add tickers or `cse_sector` values to `EXCLUDED_SECTORS` / `EXCLUDED_TICKERS` in config when you have a list. |
| 9 | LLM-assisted financial-statement extraction | **Not wired in** — `app/domain/financial_statement_parsing.py` does deterministic (regex/heuristic) extraction of a specific subset of line items instead; see its module docstring and README_ENDPOINTS.md gap #7 | Master Spec §5 calls for "PDF table extraction -> LLM-assisted line-item mapping." Actually calling an LLM needs an API key, a model choice, and a cost budget — none of which should be decided silently in code. The deterministic extractor covers total/subtotal-level balance sheet and income statement lines, PLUS (17 Aug, verified against TWO independent real filings — J.F. Packaging PLC and Swadeshi Industrial Works PLC's FY2025/26 statements of cash flow, deliberately sought out to check whether the first company's wording generalised; it didn't, every line is worded differently between the two) cash-flow-statement lines: `cash_flow_from_operations`, `net_increase_in_cash` (both companies' own wording), `capital_expenditure` (Swadeshi's wording — J.F. Packaging's equivalent label wraps across two physical lines and this extractor has no label-continuation logic), and `depreciation_and_amortisation` — J.F. Packaging prints this combined on one line; Swadeshi prints Depreciation and Amortization as two SEPARATE lines instead, which `derive_additional_line_items` (same module) now sums into the same canonical figure, wired into ingestion as a second "derived draft" pass (`build_derived_fundamental_drafts`) whose `source_snippet` cites both components rather than pretending to quote one printed line. **Same-day update: the working-capital gap is closed too, for Swadeshi specifically.** Rather than summing an unpredictable, company-varying set of individual working-capital lines (4 on Swadeshi's filing, 5 differently-named ones on J.F. Packaging's), `change_in_net_working_capital` is derived from the statement's own two bookend subtotals — "Operating Profit before Working Capital Changes" (verified byte-identical wording on BOTH real filings) minus "Cash generated from Operations" (needed a second wording, same as every other cash-flow line here) — via the same `DERIVED_DIFFERENCES` mechanism `derive_additional_line_items` already used for D&A's `DERIVED_SUMS`. **Swadeshi is therefore the first real company with ALL THREE of DCF's required cash-flow inputs individually extractable** — capex direct, D&A derived, working capital derived — verified end-to-end against the live downloaded PDF, not just the test fixture. `app/domain/dcf.py`'s own module docstring has the full picture, including why this still doesn't mean DCF is wired up: extraction proving one period's figures exist is not the same as the multi-year forecast wiring (§18.2's growth/margin/tax fade assumptions) a live DCF run needs, and that wiring is real, separate, not-yet-built work, not a data gap anymore. Segment data, note-level detail, and non-4-column-format companies all still need either broader deterministic rules or the LLM step this row is tracking. **Higher-leverage now than when this row was written**: `financial_reports_archive_loader.py` (17 Aug) feeds years of real filings per company through this SAME extractor, so both its remaining gaps AND its new cash-flow coverage compound across many more real periods rather than the two filings verified. §14's earnings-integrity signals still need Beneish/related-party/audit data this row doesn't touch, so they stay unanswerable — but §16's cash-flow routing question is now genuinely half-answerable (CFO's sign, not yet "predictable," which needs multi-period history — see `app.domain.valuation_router`'s own docstring). DDM (`dividend_residual_income.py`) still lacks dividend history entirely, a wholly separate gap. Residual income and justified P/B remain the two Phase 3 models that run as full live triangulation anchors (book value, ROE and Ke are all already extracted/computed). **Same-day, third update: `app.domain.valuation_view.current_period_fcff_for` now computes a real, live FCFF number too** — §18.1's formula (`app.domain.dcf.compute_fcff`, extracted from the multi-year projection loop as its own reusable function) applied to Swadeshi's one confirmed period, deliberately informational only and never fed into triangulation — an undiscounted single period is not a per-share fair value. Three new §12 ratios (`cash_conversion`, `operating_cash_flow_margin`, `sloan_accrual_ratio`) moved from `NOT_YET_COMPUTABLE` to real, tested formulas as a direct result of this same CFO extraction. **Fourth, same-day update: §18.1's WACC (as opposed to Ke) is now live too.** `total_interest_bearing_debt` and `interest_expense` both extract from Swadeshi's real balance sheet/cash-flow statement — the debt line needed a genuinely new capability, `SUM_ACROSS_OCCURRENCES`, because "Interest Bearing Loans and Borrowings" prints TWICE, byte-identically, as the standard current/non-current maturity split; summing both (not keeping only the first, which the ordinary dedup rule would have done) gives the correct total. New module `app/domain/wacc.py` computes cost of debt and WACC properly — and is explicit that a missing cost of debt is NEVER defaulted to zero the way `cost_of_equity.py`'s premiums are, because that would understate WACC and overstate every DCF value built on it, the dangerous direction. Wired live via `app.domain.valuation_view.wacc_for`. **This still doesn't mean DCF is close to live, though — a THIRD, newly-precise gap surfaced while checking**: `DCFAssumptions.working_capital_pct_revenue` needs the working-capital STOCK (a balance-sheet level), not the working-capital CHANGE (a flow) this system already extracts; no canonical label maps the individual current-asset/current-liability components a stock figure would need. `app/domain/dcf.py`'s own docstring has the full, current picture. **Fifth, same-day update: the working-capital STOCK gap above is closed, and closing it surfaced a real bug.** `derive_additional_line_items` gained a third derivation shape — rather than a fixed 2-key sum or difference, `net_working_capital` sums whichever of a company-varying frozenset of current-asset canonical keys (trade receivables, inventories, advances and prepayments, related-party amounts) are actually present, minus whichever current-liability keys are present, verified on both real filings' genuinely different component sets and cross-checked against each company's own Total Current Assets/Liabilities minus known non-operating items. **While re-running the full extraction against J.F. Packaging's actual PDF to verify this (not just the test fixtures), `total_interest_bearing_debt` came back exactly DOUBLE the correct figure** — 2,696,038 instead of 1,348,019. Root cause: J.F. Packaging's Note 25 page is subtitled "25.1. Financial Instruments - Statement of Financial Position", which itself contains the phrase "statement of financial position" — one of the primary-statement-page markers — so the page-marker filter let a notes page through, and `SUM_ACROSS_OCCURRENCES` summed the note's verbatim reprint of the same two debt figures as if they were a third and fourth real occurrence. Fixed with an unconditional `notes to the` exclusion checked before any positive marker (`_is_primary_statement_page`), verified against BOTH companies' real PDFs post-fix — J.F. Packaging's debt correctly returns to 1,348,019 from the balance sheet page alone; Swadeshi's correctly returns 645,836,104 (its own genuine current/non-current split, both entries on the balance sheet page, not a notes-page artifact) while its three notes pages mentioning the same debt label are now excluded. `interest_expense` also gained J.F. Packaging's own wording ("Interest Expense", distinct from Swadeshi's "Finance Costs"). A permanent regression test uses the real note text as its fixture. This is the extraction pipeline's most serious bug found this session, and it was found only by re-running the complete real document, not the unit-test suite — the reason live-data verification stays mandatory even after a feature is "tested." |
| 10 | Equity risk premium (§17.1/§17.2) | `erp_effective_pct` **defaults to 7.0%**, a round, provisional placeholder — NOT sourced from Damodaran's live country dataset, which this system has no access to. §17.1 explicitly wants ERP_effective "reviewed semi-annually against Damodaran's country dataset and against the ASPI implied premium." The ASPI-implied half of that cross-check IS live — `app.domain.cost_of_equity` surfaces it as `implied_erp_cross_check` (the same computation as §29's hero spread, read as an ERP estimate rather than a cheap/expensive signal) — but it is displayed alongside `erp_effective_pct`, never silently substituted for it. | Ke (§17.2) is the discount rate every valuation model in Phase 3 will use. A wrong ERP moves every fair value in the system by the same proportional amount, so this is the single highest-leverage number in PARAMETERS.md to get right before Phase 3's actual valuation math (§18-24) is built on top of it. |
| 11 | Long-run nominal growth `g` (§18.2, §19.1, §20.2) | `long_run_nominal_growth_pct` **defaults to 5.0%**, a round, provisional placeholder — Sri Lanka's long-run nominal GDP growth is not a series any ingested source publishes, same category of gap as row #10's ERP. Every steady-state formula (DCF terminal growth, Gordon growth, justified P/E and justified P/B) needs a single stable `g`, and until this row was added (17 Aug, when `app.domain.valuation_view` first needed a concrete number to wire justified P/B and residual income to live data) nothing in this system had ever needed one. Added mid-build for the same reason row #9 was: it became a real, concrete choice rather than an abstract one. | Same leverage direction as ERP but smaller in practice, because §18.2 already caps `g` at `Rf_LKR` (≈10-12% on the current CBSL-scraped T-bill) — a wrong `g` below that cap still moves every steady-state fair value, just with less room to compound than ERP does through the whole discount-rate term. |

## Other defaults baked into Phase 1 code (not in Part O, but worth flagging)

- **Reporting lag defaults** (§6): 90 days for quarterlies, 180 days for
  audited annuals, per-company override via `securities.reporting_lag_days`.
- **Annual factor formation date**: 30 September (§6, §35.1) — not editable
  per-company, this is a market-wide convention in the spec.
- **cse.lk rate limiting**: minimum 2 seconds between calls, exponential
  backoff, circuit breaker after 5 consecutive failures (§5, "the single
  biggest operational fragility"). Configurable but defaults are deliberately
  conservative.
- **Reconciliation mismatch threshold**: 0.5%, matching §7 exactly.
